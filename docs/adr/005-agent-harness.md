# ADR 005: AI 에이전트 하네스(Agent Harness) 체계 도입

## 1. Status
- Accepted

## 2. Context (배경)
기존에는 `AGENTS.md`에서 시작하여 각 프로젝트의 컨텍스트 문서로 이어지는 연쇄적 마크다운 참조 방식을 사용했습니다. 그러나 프로젝트의 규모가 커지고 컨텍스트가 깊어짐에 따라, 이 방식만으로는 AI 에이전트의 할루시네이션(Hallucination, 지시사항 망각 및 임의 코드 생성)을 완벽하게 통제하기 어려웠습니다.
따라서, 서로 다른 레벨의 프로젝트라 하더라도 AI가 공통으로 준수해야 할 '행동의 틀(Harness)'을 강력하게 규정할 수 있는 구조가 필요하다고 판단했습니다.

## 3. Decision (결정 사항)
AI 에이전트의 행동을 제어하고 초기 진입을 강제하는 **단일 진입점(Bootstrap Harness)** 체계를 도입합니다.
- 새로운 프로젝트나 태스크를 시작할 때는 반드시 `BOOTSTRAP_HARNESS.md`를 첫 프롬프트로 주입합니다.
- 워크플로우: `BOOTSTRAP_HARNESS.md` (글로벌 규칙 강제) $\rightarrow$ `AI_PROJECT_CONTEXT.md` (프로젝트 로컬 규칙) $\rightarrow$ 하위 단계(State Machine 기반) 순서로 작업을 진행하도록 에이전트의 상태를 통제합니다.

## 4. Consequences (예상되는 결과)

### 장점 (Positive)
- **할루시네이션 방지**: 명확한 제약 조건(XML 태그 기반)을 통해 에이전트가 마음대로 코드를 완성해버리는 현상을 원천 차단합니다.
- **멘토링 퀄리티 및 일관성 유지**: 어느 레벨의 프로젝트를 진행하든 일관된 교육 철학(스켈레톤 우선 등)을 유지할 수 있습니다.

### 단점 및 고려사항 (Negative/Risks)
- **유연성 저하 우려**: 하네스 구조가 너무 엄격하게 강제될 경우, 창의적이거나 유연한 문제 해결이 어려워질 수 있습니다. 이를 보완하기 위해 하위 단계(프로젝트/태스크 레벨)에서는 유연한 대처가 가능하도록 하네스 내부의 State 설계를 열어두어야 합니다.
- **컨벤션 충돌 방지**: 기존에 작성된 `ADR-004`(네이밍 및 코드 컨벤션)와 새롭게 정의되는 하네스 내의 규칙이 충돌할 가능성이 있습니다. 지속적인 리뷰를 통해 두 문서 간의 조율이 필요합니다.
